# Writing

Write for the person who needs to understand, decide, or act. The document is
successful when that person can do so without rereading it.

## Start with the point

State the outcome, decision, or purpose first. Add context only when it changes
the reader's understanding. Prefer a concrete example over a broad claim, and
say what is uncertain instead of hiding it behind confident language.

Choose the smallest structure that makes the material easy to scan. A short
paragraph is often better than a hierarchy of headings and lists.

## Use direct language

- Use concrete subjects and strong verbs. Prefer active voice.
- Address the reader as “you” when giving instructions.
- Put a condition before the action it controls.
- Remove throat-clearing, repetition, clichés, and unnecessary jargon.
- Avoid calling a task easy or obvious. Describe the required action instead.
- Use descriptive link text and sentence-case headings.
- Let technical terms carry precision, not status. Define unfamiliar terms once.

## Fit the artifact

A README should establish what the project is, why it exists, how to reach a
first useful result, and where to learn more. Link to detailed material instead
of duplicating it.

A pull request description should help a reviewer understand the outcome,
motivation, review path, evidence, and risk. It should not replay the author's
work session.

A design document should make the decision visible. Explain the constraints,
the chosen approach, meaningful alternatives, and consequences.

Revise for the reader's attention. Delete any sentence that does not help them
understand, decide, or act.
