# Quality

## Pages

A page starts at its decision or its material, with no lede and no
rationale before it. Each option carries one line of consequence. A
sentence that could sit unchanged on another plan says nothing about this
one.

Where the plan could go more than one credible way, show each way as an
option, recommend one, and show the basis for the recommendation. An
option is a different plan, not a different label. Do not invent an
alternative when only one way is credible. The component index says what
each component is for.

Build each page around the proposal. Where the browser can show the
material, rendered, drawn or demonstrated, show it, and use prose for the
context and consequences the page cannot show. Resolve routine details
from the project and the settled requirements instead of asking.

The user comments on any text or component without being asked, so a page
does not ask what the user thinks of it. A question asks for context the
user has and the plan cannot get from the project, and sits next to the
proposal it affects; questions that belong to no page get a page of their
own.

Use hierarchy and color to direct attention, never as the only carrier of
meaning. Add no decorative cards, labels, tags or pills that repeat nearby
text.

## Exploration

Exploration pages settle open decisions, one page per topic. There is no
overview, summary or early implementation page; Agreed is the only running
context. A revision puts every open point on the pages at once, so the
reviewer settles them in one round. A revision with one question on one
page has not explored enough to ask the rest.

The final plan is assembled from Agreed: a decision that is not on Agreed
is not settled and cannot bind a step. Each revision closes open points.
When the user asks you to decide, decide, record it on Agreed, and go on.
When the user asks for a certainty the project cannot give before
implementation, say what implementation will find out, how, and what
result is acceptable. Two revisions in a row that close nothing mean the
plan is ready to present with its open items named.

## Review

Present the complete plan as a handoff organized around the changes an
engineer will make: an overview page with the outcome, the scope and the
relationships among the steps, linked to one page per step. Each step
states the behavior it must produce, its dependencies, its exact
interfaces, the approved material, the constraints and how the behavior
will be verified, and says which parts bind, which illustrate, and which
checks are automated.

Carry approved wording, code, interfaces and mocks into the step from the
latest revision that showed them, embedded, not summarized or linked. The
plan and the project must be enough to implement and verify the work
without earlier revisions or the conversation. Say why an unknown must wait
for implementation, what to investigate, and what result is acceptable.
Match the detail to the work.

## Iterating

When a proposal changes between revisions, show the change against what
the user reviewed: a diff for text and code, before and after for visuals.
Silence on a passage is agreement, so the diff is what the user reads
next. Remove a decision or question in the revision that records its
answer on Agreed; a control that stays looks unanswered and gets answered
again. If the topic is still open, ask the next question, never the same
one.
