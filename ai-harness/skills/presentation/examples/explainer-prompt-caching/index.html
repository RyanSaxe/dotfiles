§ 2 · Mental model

Mark a point. Anything before it gets cached.

SYSTEM 50,000 tokens — instructions, persona, rules
TOOLS 8,000 tokens — function schemas, examples
↳ cache_control breakpoint everything above is the cache key — fingerprinted, 5-min TTL
USER 200 tokens — the actual question
Match the fingerprint within 5 minutes → you pay 10% of the usual rate to read it back.

§ 3 · The math

What it actually saves.

Cached request

$$\text{cost} = 0.10 \cdot \text{base} + \text{new}$$

You pay 10% to read back the cached prefix, plus the regular rate for new tokens.

First write

$$\text{cost} = 1.25 \cdot \text{base}$$

The first request writes the cache and pays a 25% premium for the privilege.

Break-even hits at ~2 requests within 5 minutes. After that, savings compound fast.

§ 5 · In code

Minimal example.

client.messages.create(
    model="claude-opus-4-7",
    system=[
        {
            "type": "text",
            "text": LARGE_SYSTEM_PROMPT,
            "cache_control": {"type": "ephemeral"},
        },
    ],
    messages=[{"role": "user", "content": user_question}],
)
cache_control is a marker, not a setting. It says "everything up to here is the cache key."

§ 6 · Common mistakes

Three ways people accidentally turn it off.

  1. Putting the breakpoint in the wrong place.

    If anything above the breakpoint changes per request, you cache-miss every single time. Move it down past the dynamic stuff.

  2. Inserting a timestamp.

    Even one dynamic byte before the breakpoint invalidates the prefix. Common with logging headers, request IDs, and date-stamped instructions.

  3. Letting traffic go cold.

    Five minutes of silence and the cache evicts. Spiky workloads benefit less than steady ones — you pay the write premium repeatedly.

§ 8 · Applicability

Good fit, poor fit.

Good fit

Use it when…

  • Long, stable system prompts (10k+ tokens)
  • Repeated tool / schema definitions
  • Multi-turn conversation prefixes
  • RAG over a slow-changing corpus
  • Steady traffic, not spiky
Poor fit

Skip it when…

  • One-off requests
  • Prompts under ~1k tokens
  • Highly dynamic prefixes
  • Sub-5-minute idle gaps
  • Each request is unique

§ 9 · Recap

Three things to remember.

i.

The breakpoint is the cache key.

Anything above it is fingerprinted. Anything below is fresh on every request.

ii.

~2 requests is break-even.

You pay a write premium on the first one. After that, savings compound fast.

iii.

Stable prefixes win.

Dynamic prefixes lose. The whole game is keeping bytes above the breakpoint identical.
